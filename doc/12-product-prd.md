## 0. 一页结论

OfferChaser 解决的不是“帮用户多点几次投递按钮”，而是把求职投递这件高重复、高风险、结果不确定的事情，做成一条**可配置、可解释、可审计、出错时不乱发**的本地流水线。

产品从零到现在，主线始终没有变：

1. 把 BOSS 岗位采集下来；
2. 先用本地硬规则缩小范围；
3. 再用 AI 做匹配判断和沟通话术；
4. 发送前核对联系人、会话身份、每日额度和文字/图片结果；
5. 不确定就停住，把决定权交还给用户；
6. 所有任务、评估、投递、预算、人工操作留痕，形成下一轮的输入。

当前 2.0.1 已经覆盖：

- 本机投递执行闭环；
- 规则/AI/身份/额度/文字/图片六层安全约束；
- 人工放行、UNKNOWN 核对、有效沟通跟进、图片补发等人机协同闭环；
- 方向模板与 AI 简历建模板；
- 首页岗位解读（粘贴 BOSS 链接，只读生成公司/岗位/匹配/风险/沟通话术）；
- 5 空间管理台、洞察页重构、移动端底部导航；
- 默认免登录的本机管理台（保留可选认证开关）。

这不是一个追求“全自动无人值守”的产品。它的产品价值恰恰在于：**把不该自动化的判断保留给人，把重复劳动交给机器。**

## 1. 背景与问题

### 1.1 用户处境

一个正在找工作的用户，每天会在 BOSS 直聘上重复做这些事：

- 反复搜索相同或相近的关键词；
- 打开几十个岗位详情，判断岗位和简历是否匹配；
- 复制、修改打招呼话术；
- 担心发错 HR、发错岗位、重复打扰；
- 投递后记不清哪些投了、哪些回了、哪些需要跟进；
- 想复盘“为什么今天投了 30 个，回复只有 2 个”。

这些动作单独看都不难，但每天重复，且存在不可逆的对外发送，容易产生四类损失：

1. **时间损失**：大量重复阅读和手工操作；
2. **机会损失**：好岗位没被及时处理，或话术没有突出匹配点；
3. **关系损失**：重复打扰、发错对象、在 HR 已回复后继续自动跟进；
4. **信任损失**：结果未知却按成功统计，用户无法判断系统到底做了什么。

### 1.2 现有方案的不足

- 纯人工：可控，但效率低、不可复盘；
- 纯自动脚本：效率高，但误发、漏记、绕过平台规则的风险不可接受；
- 通用自动化工具：能点击，但不理解“岗位匹配、会话身份、发送确认、结果未知”这些业务语义。

### 1.3 产品机会

把投递拆成可验证的环节，每个环节都可以配置、观察、暂停、人工接管；只在证据充分时继续，证据不足时 fail-closed。

## 2. 产品定位

### 2.1 一句话定位

> 一个只在本机运行、面向单个求职者的 BOSS 直聘投递与求职决策工作台。

### 2.2 目标用户

- 正在主动求职、每天需要处理较多 BOSS 岗位的单个用户；
- 愿意配置关键词、规则和 AI，但不希望把账号交给云端 SaaS；
- 接受“重要动作要人工确认”，不接受“系统替我乱发”。

### 2.3 非目标

- 不做多用户、多租户、云端 SaaS；
- 不做多招聘平台聚合；
- 不做无人值守定时投递；
- 不自动回复 HR、不自动执行跟进；
- 不绕过 BOSS 风控、验证码、登录校验；
- 不承诺投递成功率、回复率或面试率；
- 不把 AI 输出当作不可质疑的最终事实。

---

## 3. 产品原则

### 3.1 安全优先于自动化率

如果一个环节无法确认，产品选择“停住”，而不是“猜着继续”。

具体表现为：

- 会话身份不明：不发送；
- 联系人已回复/拒绝/接管/停止：不自动沟通；
- 每日额度不足：不发送；
- 文字结果 UNKNOWN：不记成功；
- 图片结果 UNKNOWN：不并入文字成功；
- AI 调用失败：不回退原文或固定话术；
- 规则/AI REVIEW：进入人工队列，不自动发送。

### 3.2 人机分工

机器负责：

- 采集、去重、规则初筛、AI 匹配、话术草稿、台账、统计。

人负责：

- 是否开始真实投递；
- 高风险 REVIEW 是否放行；
- UNKNOWN 是否实际已发送；
- 跟进是否批准；
- 是否人工接管或停止联系。

### 3.3 可解释、可审计

系统必须能回答：

- 这个岗位为什么被过滤？
- 这条消息为什么没发？
- 这轮任务为什么停了？
- 这笔额度为什么被占用？
- 这个人为什么还在待办里？
- 这个数字按什么口径算出来？

### 3.4 本地优先

- 数据、登录态、数据库、备份默认都在本机；
- 不允许把 token、Cookie、API Key、简历、岗位数据提交到仓库；
- BOSS 与 AI 是仅有的外部依赖；
- 岗位解读不对公网暴露服务。

## 4. 从 0 到当前版本的演进

### 阶段 0：验证“能不能跑通”

**目标**：先证明一条最小投递链路能跑。

**范围**：

- BOSS 登录态；
- 按关键词/城市搜索；
- 打开岗位详情；
- 规则判断；
- 打开聊天；
- 发送招呼语；
- 落一笔投递记录。

**阶段结论**：

能跑通，但“发出去”不等于“发对了”。只做点击自动化不足以支撑真实求职场景。

---

### 阶段 1：把“发出去”变成“可确认地发出去”

**问题**：只看点击成功，会把“没发出去”“发错人”“发重复”都误判为成功。

**新增能力**：

- 岗位快照：JD、薪资、公司、行业、融资、规模、地址、HR、岗位链接；
- 规则三态：PASS / REJECT / REVIEW；
- AI 严格 JSON：MATCH / REJECT / REVIEW / ERROR；
- 话术约束：长度、开头匹配点、禁止寒暄；
- 联系人状态：UNKNOWN / REPLIED / REJECTED / INTERVIEW / NO_REPLY；
- 每日首次沟通额度：原子预留、结果未知保守占用、结算可追溯；
- 聊天身份核对：HR、岗位、公司、会话标题；
- 文字发送 15 秒独立确认；
- 图片简历 45 秒独立确认；
- UNKNOWN 不记成功；
- 任务、评估、投递、事件全部落库。

**阶段结论**：

产品从“自动化脚本”变成了“可解释的投递系统”。

---

### 阶段 2：把异常交给人

**问题**：系统再谨慎也会遇到页面异常、身份无法核对、发送结果未知。

**新增能力**：

- 待办中心：
  - 待核对：UNKNOWN 的人工判定；
  - 待放行：规则/AI REVIEW 的人工批准；
  - 建议跟进：人工批准后下一轮执行；
  - 图片补发：文字已确认但图片失败/未知时生成计划；
- 人工核对三态：
  - SENT：改为已确认，结算额度；
  - NOT_SENT：改为失败，释放预留；
  - STILL_UNKNOWN：只记录说明，不改状态和额度；
- 一键清理待核对：仅写 STILL_UNKNOWN，只清列表，不伪造成功；
- 人工放行：批准只入队，执行时重新 AI 评估，仍走身份、额度、文字+图片确认；
- 状态同步：读取 HR 已读/已回复，不回写成功、不自动发消息。

**阶段结论**：

产品形成了“机器执行 + 人工兜底”的闭环，而不是遇到异常就失败。

---

### 阶段 3：把配置变成产品

**问题**：不同求职方向需要不同的关键词、规则、AI 画像和简历，不能每次改一堆全局配置。

**新增能力**：

- 方向模板：搜索条件、规则、AI 介绍/提示词、图片简历、采集策略、投递开关；
- 模板激活：下一轮任务按模板校正当前配置；
- AI 帮我建模板：
  - 上传简历图片 / 粘贴简历文本；
  - 可选补充说明（优势、技能、经验、项目）；
  - AI 画像 → 推荐方向/薪资 → 5 个问答 → 草稿预览；
  - 默认不激活、不自动投递；
- 模型服务配置：BASE_URL、模型名、API Key 本机保存；
- 模板保存与全局 AI 配置的覆盖保护。

**阶段结论**：

产品从“一个能跑的脚本”变成了“可复用、可配置的求职工作台”。

---

### 阶段 4：把管理台变成决策中枢

**问题**：功能变多后，页面不能只是表格堆叠，需要让用户知道现在发生了什么、下一步做什么。

**新增能力**：

- 5 个空间：今日 / 待办 / 记录 / 配置 / 洞察；
- 今日：运行状态、KPI、9 阶段管线、事件流、额度环、状态同步；
- 待办：核对、放行、跟进、补发统一决策；
- 记录：投递、评估、任务、联系人；
- 配置：模板、规则、AI、模型服务；
- 洞察：效果与采集、跟进策略；
- 三套主题（瓷白靛 / 石墨铜 / 象牙松）；
- 统一 DialogShell、焦点陷阱、键盘可达；
- 移动端底部空间导航；
- 洞察页重构：结果卡、趋势、处理流水、采集概况、明细和口径抽屉。

**阶段结论**：

用户不需要读数据库或日志，就能回答“今天发生了什么、哪里卡住了、下一步点哪里”。

---

### 阶段 5：从投递工具走向求职决策助手

**问题**：投递完成后，用户仍要自己理解公司、岗位、风险和怎么和 HR 沟通。

**新增能力**：

- 首页岗位解读：
  - 粘贴 BOSS 岗位链接；
  - 使用已登录浏览器只读打开；
  - 解析岗位/公司/薪资/地点；
  - 结合当前模板画像生成岗位总结、公司解读、匹配点、缺口、风险、沟通建议、开场话术、HR 追问回复；
  - 明确只读，不自动发消息、不投递；
- 首页“跟进待办”升级：
  - 识别 HR 已回复 / 面试中；
  - 只保留简历附件已确认送达的沟通；
  - 点击查看公司、岗位、薪资、岗位页；
- AI 建模板补充说明输入；
- 批量清理待核对；
- 默认取消管理台登录门，本机直接进入；保留可选认证开关。

**阶段结论**：

产品从“投递执行器”扩展为“投递 + 沟通准备”的求职决策助手。

## 6. 功能需求

### FR-01 任务与运行控制

| 项 | 需求 |
|---|---|
| 启动 | 用户手动点击开始，系统不得自动开始真实投递 |
| 状态 | IDLE / RUNNING / STOPPING / COMPLETED / FAILED / PAUSED_VERIFICATION |
| 停止 | 托盘/管理台停止，等待 worker 退出，超时才兜底 |
| 事件 | 每次阶段变更写入事件流，最近 30 条可见 |
| 保护 | 未登录 BOSS、worker 未退出、额度不足、验证中断时不允许继续 |

**验收**：用户能看懂当前运行到哪一步、为什么停、下一步能做什么。

---

### FR-02 采集与岗位快照

- 支持关键词、城市、行业、经验、学历、薪资、规模、融资、职位类型；
- 有限增量采集：每关键词上限、时长上限、连续无新增窗口；
- 同一岗位按可信 ID 去重；
- 快照统一供规则、AI、台账、岗位解读复用；
- 解析不到 JD 的岗位不得进入发送链路。

---

### FR-03 本地规则

- 硬规则先行，规则不通过不调用 AI、不打开聊天；
- 输出 PASS / REJECT / REVIEW；
- REVIEW 进入人工放行队列；
- 规则必须版本化，规则变更可追溯；
- 支持 URL/文本 JD 的规则预览（不发送）。

---

### FR-04 AI 匹配与话术

- 任意 OpenAI 兼容接口；
- 严格 JSON，禁止 markdown/解释；
- 输出 decision / analysis / message；
- analysis ≤80 字；
- 话术长度和匹配点约束；
- AI 失败、超时、非法 JSON 一律不发送；
- 不得回退默认话术或原文。

---

### FR-05 安全发送链路

固定顺序：

```text
联系人复检
→ 额度原子预留
→ 打开聊天
→ 会话身份核对
→ 文字发送独立确认
→ 图片简历独立确认
→ 结果落库
```

任一环节失败或无法确认：

- 不发送；
- 记录原因；
- 额度按规则释放/占用；
- 不把 UNKNOWN 记成功。

---

### FR-06 联系人、跟进与人工放行

- 联系人状态：UNKNOWN / REPLIED / REJECTED / INTERVIEW / NO_REPLY；
- 回复、拒绝、面试、人工接管、停止联系会取消未执行跟进；
- 跟进计划：SUGGESTED → APPROVED → EXECUTED / REJECTED / CANCELLED；
- 跟进必须人工批准，只在下一轮任务遇到同一岗位时执行；
- 人工放行：REVIEW 批准后只入队，执行时重新 AI 评估；
- 首页跟进待办只展示：
  - REPLIED / INTERVIEW；
  - 至少一次图片简历确认送达；
  - 附带公司、岗位、薪资、岗位页。

---

### FR-07 UNKNOWN 核对与批量清理

- 待核对列表来自 UNKNOWN 投递；
- 单条三态：SENT / NOT_SENT / STILL_UNKNOWN；
- 原因必填，写审计；
- 二次确认；
- 一键清理只使用 STILL_UNKNOWN，只清列表，不记成功、不结算/释放额度；
- 不支持把批量清理结果伪造成成功。

---

### FR-08 模板与 AI 建模板

- 模板是完整配置快照；
- 激活后下一轮生效；
- AI 建模板支持图片/文本简历；
- 支持补充说明（≤1000 字），仅本次分析，不保存；
- 生成草稿默认不激活、不开始投递；
- 保存时只回写实际修改的 AI 字段，避免旧值覆盖全局提示词。

---

### FR-09 岗位解读（C 路线第一版）

- 首页输入 BOSS 岗位链接；
- 仅接受 BOSS 域名 `/job_detail/` 链接；
- 使用程序已登录浏览器只读打开；
- 解析岗位、公司、薪资、地点、经验、学历、行业、融资、规模；
- 结合当前模板画像，输出：
  - 岗位总结
  - 公司总结
  - 匹配点
  - 缺口
  - 风险（需核实）
  - 沟通建议
  - 首次沟通话术
  - HR 追问回复
  - 建议问 HR 的问题
  - 首次沟通避免主动提的内容
- 只读：不自动回复 HR、不投递、不改联系人；
- AI 结论标注“需自行核实”；
- 当前不接入外部新闻/工商/面经来源。

**验收**：粘贴真实链接后可展示结构化解读；单次等待约几十秒；失败给出可操作错误。

---

### FR-10 洞察

- 页头只保留一个 H1「洞察」；
- 效果与采集 / 跟进策略在 H1 右侧；
- 吸顶工具栏：范围分段、刷新、更新时间、口径说明；
- 4 张结果卡：确认投递、回复率、新发现岗位、今日首次沟通额度；
- 趋势图只保留三项指标：确认投递 / 新发现岗位 / HR回复；
- 处理流水按环节展示自身占比，不做跨环节转化率；
- 采集概况 6 格；
- 明细按日/按关键词；
- 口径说明使用右侧抽屉；
- 单日不画趋势，全零不伪造趋势；
- 未知单独标色，拒绝使用中性色。

## 7. 关键用户流程

### 7.1 首次使用

```text
启动 OfferChaser
→ 打开管理台（默认免登录）
→ 配置模型服务
→ 创建/激活方向模板
→ 上传图片简历
→ 检查规则与额度
→ 点击开始投递
```

### 7.2 正常投递

```text
采集 → 规则通过 → AI 匹配 → 联系人复检
→ 额度预留 → 身份核对 → 文字确认 → 图片确认
→ 落库 → 统计
```

### 7.3 规则/AI REVIEW

```text
规则/AI REVIEW
→ 进入待放行
→ 用户查看原因
→ 批准/拒绝（必填原因）
→ 批准只入队
→ 下一轮重新 AI 评估
→ 仍走完整安全链路
```

### 7.4 UNKNOWN

```text
文字/图片结果未知
→ 进入待核对
→ 用户去 BOSS 聊天核实
→ SENT / NOT_SENT / STILL_UNKNOWN
→ 额度与状态按结论调整
```

### 7.5 有效沟通跟进

```text
HR 回复 / 面试
→ 首页跟进待办出现
→ 查看公司、岗位、薪资、附件状态
→ 点击岗位页
→ 视情况在待办中处理建议跟进
```

### 7.6 岗位解读

```text
首页粘贴 BOSS 链接
→ 只读打开岗位页
→ 解析岗位/公司字段
→ 结合当前模板画像
→ AI 输出匹配、风险、沟通建议、话术
→ 用户自行决定是否沟通
```

## 8. 数据与指标口径

### 8.1 核心口径

| 指标 | 口径 |
|---|---|
| 确认投递 | 文字确认成功的唯一 attempt |
| 图片已发 | 图片状态 CONFIRMED |
| 文字结果未知 | 单独统计，不计成功 |
| 规则过滤率 | 规则拒绝 ÷ 规则评估 |
| 回复率 | 已回复 ÷ 文字确认成功 |
| 今日首次沟通额度 | 当日计，不随日期范围变化 |
| 有效沟通跟进 | REPLIED/INTERVIEW 且至少一次图片确认送达 |
| 新发现岗位 | first_seen_at 在范围内的去重岗位 |
| 旧数据 | 缺 first_seen_at 的 legacy 数据，单独列示 |
| 采集来源 | job_source 来源记录；去重岗位按 encrypt_id |

### 8.2 明确禁止的口径

- **不做跨环节转化率**：规则通过可能大于新发现，因为旧数据/跨日处理口径不同；
- 不把 UNKNOWN 并入成功；
- 不把图片失败隐藏成文字成功；
- 不把“已发送”当成“已回复”；
- 不把 AI 推断写成已核实事实。

## 9. UI / UX 要求

- 首页回答“现在发生了什么”；
- 待办回答“我现在要做什么决定”；
- 记录回答“具体发生了什么”；
- 配置回答“下一次按什么规则运行”；
- 洞察回答“整体效果如何、哪里可以优化”；
- 所有对外发送动作必须有明确确认，不允许“一键静默发送”；
- 所有只读分析必须明确标注只读；
- 颜色语义：主色=可操作/正向；拒绝=中性；复核/未知=琥珀；失败>0 才红色；
- 不依赖 CDN；图表本地 SVG/CSS；
- 支持键盘 Esc、焦点陷阱、读屏标签。

## 10. 非功能需求

### 10.1 性能

- 管理台首屏可交互 ≤ 3 秒（本机）；
- 岗位解读常规 30–90 秒（依赖 AI 与页面）；
- 趋势、明细、全量统计在本地数据量下可接受；
- AI 请求有超时，不允许无限挂起。

### 10.2 可靠性

- 数据库迁移只增量，升级前备份；
- 任务失败可定位到阶段和原因；
- 重启后额度不清零；
- 浏览器/页面异常时停住，不误发。

### 10.3 安全与隐私

- 只监听 `127.0.0.1`；
- 不提交 `.env`、`data/`、`db/`、`browser-data/`、日志；
- token、Cookie、API Key 掩码展示；
- 岗位解读不保存 `securityId`；
- 外部链接只允许 BOSS 岗位域名；
- 默认免登录是本机便利选择，不应把端口暴露到公网。

### 10.4 兼容

- Windows 10/11；
- JDK 21；
- 本机 Chrome；
- 现代 Chrome（支持 `color-mix()`）；
- 移动端 390px 可用。

## 14. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| BOSS DOM/接口变化 | 解析失败、无法发送 | 选择器自检、失败停住、人工接管 |
| AI 超时/幻觉 | 匹配误判、话术失真 | 严格 JSON、超时、人工复核、外部信息标注未核实 |
| 重复打扰 HR | 关系损失 | 联系人去重、回复后禁止自动沟通、跟进人工批准 |
| 额度超发 | 不可逆成本 | 原子预留、UNKNOWN 保守占用、先预留后发送 |
| 误记成功 | 数据失真 | UNKNOWN 不记成功、图片独立确认 |
| 本地端口暴露 | 数据/操作风险 | 仅绑定回环；默认免登录仅限本机；不转发公网 |
| 用户误操作 | 错误放行/清理 | 二次确认、原因必填、批量操作只写 STILL_UNKNOWN |

## 附录：术语表

| 术语 | 含义 |
|---|---|
| PASS / MATCH | 规则或 AI 判断通过 |
| REVIEW | 需要人工判断，不自动发送 |
| UNKNOWN | 发送结果无法确认，不记成功 |

| 人工放行 | REVIEW 岗位人工批准后进入下一轮队列 |

| 岗位解读 | 对 BOSS 岗位链接的只读分析，不发送、不投递 |
| fail-closed | 无法确认时停止，而不是猜测继续 |
